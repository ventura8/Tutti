# Tutti

*Tutti* (music): everyone plays together. Tutti lets one household share its AI subscriptions, local models,
computers and Android devices for software work, without anyone stepping on anyone else.

> **Status: 0.17.x** (see [CHANGELOG.md](CHANGELOG.md) and the [releases](https://github.com/ventura8/Tutti/releases)).
> Linux first; the installer also covers macOS, WSL and Windows. **Licence:** MIT.

## What Tutti does, in plain words

- **One main agent, many helpers.** A capable agent (Claude Code, or any other, [docs/CONDUCT.md](docs/CONDUCT.md))
  plans and reviews; bounded tasks go to cheaper workers (other CLI agents, local models), each in its own worktree,
  and every diff is reviewed and checked before it lands ([docs/WORKERS.md](docs/WORKERS.md)).
- **Accounts and usage pacing.** Tutti reads how much of each subscription is used, paces work so quota lasts until
  each reset, and moves work to an account or model with room when one runs out ([docs/USAGE-PACING.md](docs/USAGE-PACING.md)).
- **The best local AI in the house.** Tutti's own AI always uses the best free model on any household machine, falls
  back online only within pacing, and briefly goes first on that model; other work waits a few seconds and loses
  nothing ([docs/FLEET.md](docs/FLEET.md), [docs/TELEMETRY.md](docs/TELEMETRY.md#ai-assist)).
- **Machines that stay yours.** Tests and builds run on other machines through slots and leases. Each machine can have
  limited hours and a night mode; Android devices can have blocked hours; work pauses when someone is at the keyboard,
  and a machine's yield flag gives it back at once. Machines can take Cast roles, and work follows devices when they
  move ([docs/MACHINES.md](docs/MACHINES.md), [docs/DEVICES.md](docs/DEVICES.md), [docs/DISPATCH.md](docs/DISPATCH.md),
  [docs/PRESENCE.md](docs/PRESENCE.md)).
- **A main and a backup main.** One always-on machine runs Tutti; a backup takes over if it goes down and hands back
  when it returns, never both at once ([docs/FAILOVER.md](docs/FAILOVER.md), [docs/MOVE.md](docs/MOVE.md)).
- **The unblocker and the needs-input queue.** Stuck or failing work is retried with a fix, rebased or rerun by Tutti
  itself; only real decisions reach *Needs you* ([docs/NEEDS.md](docs/NEEDS.md), [docs/AUTOPILOT.md](docs/AUTOPILOT.md)).
- **It looks after itself.** Self-heal installs declared dependencies, restarts services, cleans old temp folders and
  applies updates; routine clean-ups are counted apart from real repairs ([docs/SELFHEAL.md](docs/SELFHEAL.md)).
- **GitHub connection.** Connect GitHub once from the dashboard ([docs/GITHUB.md](docs/GITHUB.md)).
- **Dashboard and chat.** A web dashboard on your LAN or VPN only, never on the public internet, with Google sign-in
  and roles. It opens on **Chat** (ask "why is the NUC idle?" or queue work), then Dashboard (usage, jobs, needs),
  **Machines** cards (one per physical computer, with WSL and desktop environments nested under it; slots busy, held back or free, and why) and Settings. An **Admin** tab is coming
  ([docs/DASHBOARD.md](docs/DASHBOARD.md), [docs/CHAT.md](docs/CHAT.md), [docs/NETWORK.md](docs/NETWORK.md),
  [docs/AUTH.md](docs/AUTH.md)).
  Automatic page updates and Settings restarts protect this tab's unsent Chat work and active answers. Cooperating Chat
  storage writers serialize on supported POSIX hosts; this does not enable simultaneous dashboard engines.

## Install

One line, then sign in. **Linux, WSL, macOS:**

```bash
curl -fsSLo tutti-bootstrap.sh https://github.com/ventura8/Tutti/releases/latest/download/bootstrap.sh && echo "17ccfd80f790fb48fc1642870b58e70a396a473bee88d279ba7ab6256eb56635  tutti-bootstrap.sh" | (sha256sum -c - || shasum -a 256 -c -) && bash tutti-bootstrap.sh
```

**Windows (PowerShell):**

```powershell
irm https://github.com/ventura8/Tutti/releases/latest/download/bootstrap.ps1 -OutFile tutti-bootstrap.ps1; if ((Get-FileHash tutti-bootstrap.ps1).Hash -eq 'CAACFE5D2E3F84B59D62263D5434EA9120E3BC10A7D2ECD6723C140A21A032C8') { powershell -ExecutionPolicy Bypass -File tutti-bootstrap.ps1 } else { 'tutti: checksum mismatch, not run' }
```

It installs Tutti and what it needs (Python through uv, gh) in your user space, checking every download's SHA-256,
then runs `tutti setup`, which asks nothing: it finds your agents and their sign-ins, GPUs and local models, machines, Android devices and
git projects, writes the config, opens each tool's own sign-in, starts the dashboard at login and turns on automatic
updates; `tutti self-update` keeps it current (on by default). Run `tutti setup` again any time: it only fills what is missing. Details, uv and pipx, and the household's
`--join`: [docs/INSTALL.md](docs/INSTALL.md).

## Quick start: use Tutti from your own agent

The one line above already ran `tutti setup`, which also connects every agent it found (`tutti connect --all`: Claude
Code, Claude Desktop, Codex, Antigravity, Cursor, Copilot, VS Code, Gemini). Then ask your agent to hand work to Tutti.
Each agent gets Tutti's MCP server and a short instruction; your other settings are kept and backed up, `tutti connect
--undo <agent>` takes it out, and the dashboard's **Connect your agent** card shows each agent's state with a Test
button. See [docs/CONNECT.md](docs/CONNECT.md). Then:

```bash
tutti config        # checks the file and names every problem with its key
tutti machines      # free slots, load and yield flag of every machine
tutti dashboard     # already running at login: http://127.0.0.1:4777/ (its Set up card lists what is left)
```

From source instead: `git clone https://github.com/ventura8/Tutti`, then `install/install.sh` (or `uv tool install
git+https://github.com/ventura8/Tutti`), then `tutti setup`. Machines you send work to need `rsync` and `ssh` with
key-based login, and Docker if you use the container runner.
Source package builds use a pinned setuptools backend and check a literal source list; see [docs/INSTALL.md](docs/INSTALL.md#other-ways).

Tutti reads one config per user, whatever folder a command starts in: `$TUTTI_CONFIG`, else `~/.config/tutti/config.yaml`
(or `~/.config/tutti/tutti.config.yaml`; `$XDG_CONFIG_HOME` is honoured), and only when neither exists the nearest
`tutti.config.yaml` from the current folder upwards. The dashboard, the MCP server, the service and every command resolve
the same file. A symlinked config stays a symlink: every save writes its real file. `tutti doctor` and Settings warn about
another copy it could pick (the XDG files, the nearest from the current folder) that differs, and merge it in with one click (`tutti doctor --merge-configs`).
Nothing personal is built in: hosts, paths and accounts live only in that file. It never holds a secret.

## The CLI

| Command | What it does |
| --- | --- |
| `tutti test <track> '<cmd>'` | Copies the track's worktree to the first fit machine and runs the command there behind the slot queue, in a memory-capped container or plain bash. `--on <machine>` skips routing; `--dir` names the tree; `--input <path>` (repeatable) copies a file or folder the job needs to that machine's cache first and hands its folder to the command as `$TUTTI_INPUTS` (read-only in a container). Returns the command's exit code. Steps a command needs first (`test.prepare`, e.g. the e2e build before Playwright) are put in front; a hot machine (`heat`) takes one run, a very hot one none. |
| `tutti test --device <name\|any> -- <cmd>` | Runs a command against an Android device on the machine its adb sees it on: `ANDROID_SERIAL` set (adb, Gradle's `connectedAndroidTest` and Playwright pick the device from it), the device's lock held so one run at a time uses it (a second waits in the same queue as machine slots), its battery, charging and heat checked first (it waits up to `--wait-minutes` for a phone to charge or cool down), the screen woken. Without a track the current folder is the tree. `--fetch <path>` copies screenshots, videos and reports back. See [docs/MACHINES.md](docs/MACHINES.md#android-devices). |
| `tutti devices [add\|pair\|move\|claim\|release\|install]` | Every Android device: connected, authorised, battery, charging, battery temperature, screen, Wi-Fi, whether a run holds it, and why it is not ready; a wireless device whose port changed is reconnected through mDNS. `pair` pairs one over wireless debugging (a QR code to scan; a TV types the code it shows; USB fallback) and adds it to the config. `move --to <machine> [devices]` moves devices to another machine with no re-pairing (the adb key is copied at mode 600), a preflight and a rollback. `add` prints the manual setup. `claim`/`release <d> --who <session>`: a session outside Tutti says it uses a device (it is released, its own settings back, only when every user is done); `install <d> <apk>`: debuggable APKs only, one install per device at a time. `hours <d> <HH-HH>[,HH-HH] [--days mon-fri]\|off`: recurring blocked hours, when the device is not used at all. See [docs/DEVICES.md](docs/DEVICES.md) and [docs/DISPATCH.md](docs/DISPATCH.md#prep-and-restore). |
| `tutti pause\|resume <kind> <name> [--stop-now] [--from <time> --until <time\|unknown>]`, `tutti optin <kind> <name> on\|off` | The dashboard's switches from a terminal: pause or resume a machine, device, worker or account (it takes nothing new; paused accounts leave the active ladder until resumed; `--stop-now` hands running jobs over first; `--from`/`--until` plan an absence), turn an opt-in item on or off. Kept in `<state>/controls.json` (the dashboard's opt-in switches write the config file, as its Settings tab does). See [docs/DASHBOARD.md](docs/DASHBOARD.md#controls). |
| `tutti files send <path>... --to <machine\|all>` | Gives files and folders (a big archive, a dataset, build inputs) to other machines over their own transport: rsync when both ends have it (resumable, skips what is there), else a resumable stream; each item is checked with `sha256sum` there. Lands in the machine's cache (`files.cache`, size budget `files.budget_gb`, least recently used items leave first) or `--dest <folder>`; `--bwlimit <KB/s>`. Refuses secrets (`.env*`, `*token*`, keys, service-account JSON, `.ssh/`). `tutti files list [--on <m>]` shows what each machine stores; `tutti files clean --on <m> [name...] [--all]` trims or empties a cache. See [docs/MACHINES.md](docs/MACHINES.md#files-for-machines). |
| `tutti ship "<message>"` | In the worktree you stand in: format, commit (with your trailer), run the targeted checks, push, deploy. `--full` runs the full checks; `--dry-run` prints the plan; `--track <t>` refuses any other worktree. Refuses to commit or push mid-rebase or mid-merge, or with conflict markers left in files (it names them). |
| `tutti usage` | Every account against its pace. Inspect recorded times and percentages on each dashboard graph by pointer, touch or keyboard. `tutti usage log <account> <percent> [--resets <time>]` records a reading; stale or missing automatic readings are shown without prompting manual entry, and cached results keep their observation time; `tutti usage read` runs the automatic readers now (Antigravity `agy /usage`, Codex CLI rate limits, scoped usage pages, Cursor, and limit messages in job logs). `tutti usage page-script [cursor]` prints the reading helper's parser for an orchestrator's browser tool to run in the owner's open usage page; `tutti usage page-reading '<json>'` records what it returned. See [docs/USAGE-PACING.md](docs/USAGE-PACING.md). |
| `tutti browser` | The household's work browser: one Chrome on one machine for every browser task (the owner's existing profile, Tutti's own, or an isolated sandboxed one), driven only through Tutti's broker (sites per task type, every action logged, one tab per task closed after). `status`, `sign-in <url>`, `sites`, `read`, `page <url>`, `remote <machine> <url>`, `isolate`, `close`. See [docs/BROWSER.md](docs/BROWSER.md). |
| `tutti owner [mode <m>]` | The owner's own prompting: the mode (`auto`, `active`, `away`, `vacation-until-YYYY-MM-DD`) and the learned weekday x hour profile. On working days the planner keeps the owner's expected burn on the main agent's accounts; on weekends, away or on vacation the workers spend it all, so every account ends near 100 % an hour before its reset. The dashboard has **I'm away until…** and a 7 x 24 heatmap. See [docs/USAGE-PACING.md](docs/USAGE-PACING.md). |
| `tutti user [name <n>\|main-agent <kind>\|main-machine <m>\|share <account> on\|off]` | Who this Tutti works for (`main-machine <m>`: your Tutti, logins and main agent move to another of your machines, as `tutti move` does): the name (default: the login's), a hashed id, the main agent (`main-agent claude|codex|agy|cursor|copilot|gemini|local` switches it: the owner reserve moves to its accounts and `tutti connect` runs for it), the config and state folders, the household role, and which accounts share the room they would lose at their reset with the household (`accounts.<n>.share_spare`, off by default). A single user is a household of one and needs nothing new. See [docs/HOUSEHOLD.md](docs/HOUSEHOLD.md). |
| `tutti household init\|join <code>\|status\|leave\|code\|serve\|project share\|unshare <repo>\|machine share\|unshare\|use\|pause\|resume <m>` | Several people in one home, one set of machines: each member keeps their own main agent, accounts and pacing; shared machines, local models and shared projects' backlogs are scheduled fairly by one coordinator. With the dashboard's Google sign-in, a new member runs one command, `tutti household join "<invite-url>"` (quoted) (from **Users**, **Invite someone**): it detects their main agent and subscriptions, opens the invite to sign in, and pairs in under a minute; without sign-in, `init` on an always-on computer prints a join code. LAN or VPN only: a public address is refused. A shared repo's tasks are published to one backlog, deduplicated across members, and leased with a heartbeat so two members' autopilots never do the same task; unreachable, a member works alone and shared tasks wait. `machine share <m>` lends a machine (and its local models) to the household, `machine use <m>` adds another member's (no login there: its owner's Tutti runs your tests in a container from a WIP ref); the coordinator grants each member a weighted fair share of its slots (prompting before background autopilots, weighted by who is expected awake, no starvation, never idle while someone has work). Accounts with `share_spare` give the room they would lose at their reset to other members' shared projects. See [docs/HOUSEHOLD.md](docs/HOUSEHOLD.md). |
| `tutti workers` | The workers and whether each is ready. Chat requires an admin-declared `chat_account_selector` and unique selector values when several accounts share a worker; see [docs/CHAT.md](docs/CHAT.md). |
| `tutti run <worker> "<task>" [files]` | Briefs a CLI worker in a worktree (`--dir`); `--show` prints the brief; `--input <path> --on <machine>` copies inputs to that machine first and tells the worker where they are. `tutti run auto` picks the worker from the latest readings: never an account in panic or spent, first one whose quota would be lost at the reset (`routing.workers` is preference order only; every `accounts.<name>.worker` still joins, with `args`). A limit message in its output logs the account as spent. With `--repo <repo>` (a folder, or a name under `autopilot.repos`) the task is handed off end to end: a worktree of the repo (new, or `--track <name>` reused; a bare name uses `autopilot.repos.<name>.path`, including from a non-git cwd), the worker headless, the diff captured, the targeted checks routed (the target repository's own: `projects.<name>.checks`, a `tutti.config.*` inside it, else `delegate.checks` / `ship.checks` when `delegate.project` is that repository or unset) and a report that says what changed, the diff's path, each check's verdict, whether coverage was checked and any tool call the CLI denied. `--check "<cmd>"` (repeatable, `--check-where local|route`) runs the given check instead of those; a local-model worker takes a delegated task through `tutti agent`'s loop. `--bg` returns at once with the id; `--discard` removes a new worktree after the report. Every run is logged with the account it spent. |
| `tutti owner window <date> <HH-HH\|off\|config>` | One day's own owner hours: the main agent's reserve follows them that day and the agents run at full speed outside them. See [docs/USAGE-PACING.md](docs/USAGE-PACING.md#a-day-with-other-hours). |
| `tutti machine limit <m> <HH-HH> [pct]\|off` | A machine's daily limited hours: Tutti uses at most pct % (default 60) of it then, for example while it hosts Plex; 0 means not used at all then. See [docs/FLEET.md](docs/FLEET.md#limited-hours). |
| `tutti workq [status\|tick]` | The compute work queue: machines with a free slot at their share run the projects' gates, tests, coverage and translation QA on the latest commits, by project priority; a failure runs again (flaky hunting) and findings become backlog tasks. See [docs/FLEET.md](docs/FLEET.md#the-work-queue). |
| `tutti fleet` | The household's local models as workers: every machine's Ollama, its models, their kinds, tier, speed and hardware. While the online accounts are ahead of their pace the autopilot sends bounded tasks to idle machines' models first. See [docs/FLEET.md](docs/FLEET.md). |
| `tutti autopilot [on\|off\|tick\|fill on\|off\|land <id>\|allow <account>]` | Hands bounded backlog work to accounts with room, or cautiously uses measured remaining quota on panicked accounts when all online agents are out and the main is local. Successful active dashboard rounds refresh resource readings and recheck pacing; the adaptive limit accounts for quota, memory, cores and cool free slots; paused and spent accounts are never used. A pass becomes a branch or pull request under the repo's policy; failures retry with their previous findings or are parked when they cannot progress. The dashboard has the toggle and panel. See [docs/AUTOPILOT.md](docs/AUTOPILOT.md). |
| `tutti dispatch [status\|on\|off\|now]` | Keep busy (on by default): idle Android devices and machines pull the pending test shards that projects declare (`projects.<p>.tests`), on every new commit, highest priority first by a weighted fair share. Heavy shards (e2e, builds, long suites) go to the strongest machine by a measured benchmark and its headroom now, light ones fill the weaker machines, and a weak machine short of room takes no heavy shard. Pause, yield, heat, battery, phone calls (paused, then resumed 30 s after the call) and opt-ins are respected, and a crashed run's lease is recovered. A device class has its own deny list (a TV never gets `wm size`, rotation or `cmd device_state`), a run that matched no test fails, and rotation and timeouts are put back after a run. A target idle more than 5 min while work waits gets a warning with the cause and a fix button on the dashboard. See [docs/DISPATCH.md](docs/DISPATCH.md). |
| `tutti presence`, `tutti job waiting\|move <id> --to <target\|auto> [--bump]`, `tutti machine evacuate <m>` | Devices and machines that come and go: each target is present, away, asleep or unknown, from the probes, heartbeats and logind. A run whose target leaves, or whose host loses power, is queued again and not counted as a failure. Absent targets are never flagged idle. Returning phones reconnect over mDNS, and a 7 × 24 profile keeps long shards off targets likely to leave. Writes are durable, autopilot attempts are checkpointed to `refs/tutti/wip/*`, and an admin can move waiting work elsewhere now. Wake-on-LAN and automatic moves are opt-in. See [docs/PRESENCE.md](docs/PRESENCE.md). |
| `tutti backlog add\|list\|rm\|seed\|retry\|done\|accept\|claim\|release\|note` | The autopilot's queue: `add <repo> "<title>" --scope <path> --check "<cmd>"`; `seed <repo>` reads FEEDBACK open items, `TODO(owner)` and the repo's `gaps` command; `retry <id> --note` sends a task back with the reviewer's notes; `accept <id>` queues a suggested candidate (a scout's Sentry triage). `claim <id> --who <session>` marks a task a session does by hand (the autopilot leaves it alone), `note <id> --note` records progress, `release` gives it back. See [docs/INTAKE.md](docs/INTAKE.md). |
| `tutti lease claim\|release\|list <machine\|device> <name> --who <session> --task <id>`, `tutti intake [--strict]`, `tutti needs ask <id> "<question>" --option ...` | All household work through Tutti: a session leases the machine or device it uses for a task, asks the owner on its task (the answer brings the task back to that session), and `tutti intake` (the dashboard's **Work outside Tutti** card) lists the commits in the autopilot repos and the leases of the last 24 h no Tutti task explains. `tutti run claude "<task>" --repo <repo>` schedules Claude-only work as a backlog task pinned to the claude worker, started under its account's pace and published by the autopilot's review policy. `tutti connect --repo <path>` adds the "all work goes through Tutti" section to a repo's AGENTS.md. See [docs/INTAKE.md](docs/INTAKE.md). |
| `tutti conduct "<goal>" [--main <agent>] [--fallback a,b]` | Another agent as the main (conductor) agent: a CLI worker (Cursor, Antigravity, Copilot, Claude Code) or a local model gets the goal and a generated instruction file: Tutti's commands as plain shell commands, the project's `AGENTS.md`/`CLAUDE.md`, the safety limits (no push, tag, merge or deploy; `ship` only with `--dry-run`; no credentials; ask-first actions stop with `NEEDS HUMAN`). Outside a run, when the main agent's accounts are in panic or spent, Tutti also hands the MAIN AGENT ROLE to the next in `main.fallback`, connects it, and writes a Chat note. `--show` prints the instructions. | `tutti connect [<agent>\|--all] [--undo\|--status [--test]]` | Wires Tutti into every main agent installed here (Claude Code, Claude Desktop, Codex, Antigravity, Cursor, Copilot CLI, VS Code, Gemini CLI): its MCP server in the agent's own config plus a skill or a marked instructions block, merged, backed up, idempotent; `--undo` removes it, `--status --test` lists each agent's state and makes a real MCP round trip. | `tutti main backup [<machine>\|auto\|none]`, `tutti failover [setup\|status\|tick\|run\|leave]`, `tutti state [size\|prune]` | A backup main machine that takes over the dashboard, coordinator, autopilot and device leases when the main machine is away, and hands Tutti back when it returns; no split brain; the state kept under its budget. | `tutti move --to <machine> [--dry-run\|--rollback\|--status] [--jobs wait\|handover]` | Moves Tutti (the dashboard, the state, the loops) to another machine in one resumable step: preflight, install, copy, freeze, final sync, the service started there, a health check (a failure rolls back), and this computer becomes a client whose commands and agents reach the new host.
